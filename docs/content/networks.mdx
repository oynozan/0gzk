# Networks & storage

Since **0.4.0**, 0gzk is multi-chain: the **`CircuitRegistry`** can live on **0G Chain** or **Base**, and circuit bundles can live on **0G Storage** or **IPFS**. **`base` is the default network**, which also makes **IPFS the default storage backend**. This page is the single source of truth for the chain presets, the storage-backend matrix, and the on-chain bundle-URI convention. Every surface (SDK, CLI, web app, examples) resolves networks the same way.

All four registries are **live and baked into the SDK** (`REGISTRY_ADDRESSES`), so no address configuration is needed on any chain. Three of them share the address `0xCe9f0DF51abeC7B8cD751067c6D8d3db5E2bE64d` (same deployer, nonce-0 CREATE); only 0G Galileo testnet differs. **`--registry`** / **`OGZK_REGISTRY_ADDRESS`** still overrides the map when you run your own deployment.

All **14 reference circuits** are published on **Base mainnet** and **Base Sepolia** with their bundles pinned to IPFS; the earlier 0G publications (5 circuits on `0g-mainnet`, 4 on `0g-testnet`, bundles on 0G Storage) are still live and resolvable. Per-chain records are committed in [`circuits/publications.json`](https://github.com/0gzk/core/blob/main/circuits/publications.json).

The 0G chains additionally carry a **0G Storage indexer** (`https://indexer-storage-turbo.0g.ai` for `0g-mainnet`, `https://indexer-storage-testnet-turbo.0g.ai` for `0g-testnet`); Base chains are plain EVM networks with no native bundle storage.

### Names, aliases, default

- **Canonical names** are the four in the table: `base`, `base-sepolia`, `0g-mainnet`, `0g-testnet`.
- **Deprecated aliases** `mainnet` → `0g-mainnet` and `testnet` → `0g-testnet` are still accepted **everywhere** a network is read (env vars, `--network`, `0gzk config set network`, `loadConfig` overrides). Prefer the canonical names in new configs.
- **Default is `base`** (chain ID `8453`) when nothing is set — **a breaking change from `0g-mainnet`** in earlier 0.4.0 builds. Because Base is `family: "evm"`, the **default storage backend flips to `ipfs`** with it: out of the box, publishing needs a pinning token instead of a funded 0G wallet, and fetching needs nothing.
- **To go back to 0G**, pick one: `0gzk config set network 0g-mainnet`, `--network 0g-mainnet` on a single command, or `OGZK_NETWORK=0g-mainnet` in the environment. Storage follows the family, so that one setting restores the 0G Storage default too.
- **Unknown names throw** (listing the valid values) instead of silently falling back. If a script relied on that silent fallback, fix the name.

Presets are exported from the SDK root as **`NETWORKS`** together with **`resolveNetwork`**, **`networkForChainId`**, **`explorerTxUrl`**, and **`explorerAddressUrl`** — see **[SDK → core](/sdk/core#networks-and-chain-presets)**.

## Storage backends

Bundle tarballs can be hosted on either backend; **`uploadBundle`** / **`fetchBundle`** and the CLI route automatically.

| | **`0g`** — 0G Storage | **`ipfs`** — IPFS |
| --- | --- | --- |
| **Upload needs** | A funded 0G wallet (`OGZK_PRIVATE_KEY`); the storage upload is a signed transaction on the `storageNetwork` chain. | A token for a `pinFileToIPFS`-compatible pinning API (`OGZK_IPFS_API_TOKEN`, e.g. a Pinata JWT). No wallet, no gas. |
| **Fetch needs** | Nothing — the public indexer serves reads. | Nothing — any public HTTP gateway serves reads (default `https://gateway.pinata.cloud`, with automatic fallback to ipfs.io, dweb.link, w3s.link). |
| **Integrity anchor** | `rootHash` = the 0G Storage Merkle root of the tarball; the storage network itself verifies the bytes. | `rootHash` = the CIDv0 sha2-256 digest (bijective with the CID), plus the registry's `vkeyHash` check after download. |
| **Default endpoints** | Indexer from the `storageNetwork` preset. | Upload `https://api.pinata.cloud/pinning/pinFileToIPFS`, gateway `https://gateway.pinata.cloud`. |

**Default backend by chain family:** 0G chains → `0g`; Base chains → `ipfs`. Since the default network is `base`, **the out-of-the-box backend is `ipfs`**: no 0G wallet is needed anywhere — a pinning token is enough to publish, and fetching needs nothing at all. Selecting a 0G network switches the backend back to `0g`. Override the pairing directly with `--storage <0g|ipfs>`, `OGZK_STORAGE`, or `0gzk config set storage`.

**`storageNetwork`** picks which 0G chain the `0g` backend signs uploads on (`0g-mainnet` or `0g-testnet`). Default: the selected network when it is a 0G chain, else `0g-mainnet`. Only relevant when `storage` is `0g`.

IPFS bundles are pinned as **CIDv0** (`Qm...`) on purpose: a CIDv0 is `base58btc` of a sha2-256 multihash with a 32-byte digest, so it is **bijective** with a `bytes32` — the digest slots straight into the registry's `rootHash` field and the CID is reconstructible from the bare hash (**`cidToRootHash`** / **`rootHashToCidV0`** in the SDK).

## Bundle-URI convention

The on-chain record's **`metadataURI`** field doubles as the bundle locator. **`parseBundleRef(record)`** applies this resolution rule when fetching by name:

1. `metadataURI` starts with **`ipfs://`** → the bundle is on IPFS at that CID. The CID's digest **must** equal `rootHash`; an inconsistent record is an error, not a fallback.
2. `metadataURI` starts with **`0g://`** → the bundle is on 0G Storage; the embedded hash must equal `rootHash`.
3. **Anything else** (empty string, an `https://` docs link, the legacy `0gzk://name@version` convention) → fetch from 0G Storage by bare `rootHash` — exactly the pre-0.4.0 behavior, so every existing record keeps resolving.

Because the convention rides on the existing `metadataURI` string field, **`CircuitRegistry.sol` is unchanged** — no redeploys were needed on 0G.

When you publish with a non-0G backend, the CLI **forces** the bundle URI into `metadataURI` (combining it with a different `--metadata-uri` is an error): an IPFS bundle is only reachable through its URI, so that slot is what keeps it resolvable. Put extra human-readable metadata inside the bundle's `metadata.json` instead.

## Cross-chain publishing and gas

Registry chain and storage backend are independent, so you can, for example, register on Base Sepolia while hosting bytes on 0G Storage (`--network base-sepolia --storage 0g`). In that split the **upload tx needs gas on the `storageNetwork` chain** and the **registration tx needs gas on the registry chain** — the same key signs both, so fund it on both chains. The CLI prints a note when a publish spans two chains. The default pairings (0G registry + 0G Storage, Base registry + IPFS) never need gas on more than one chain.

## Publish to Base Sepolia quickstart

The cheapest full walkthrough of the new stack — no 0G wallet involved:

```bash
# 1. Get a pinning-service token (e.g. a Pinata JWT: pinata.cloud → API Keys)
#    and store it once. It is masked in `0gzk config get`.
0gzk config set ipfsApiToken eyJhbGciOi...

# 2. Fund your key with Base Sepolia ETH from any Base Sepolia faucet
#    (e.g. Coinbase or Alchemy's) — the registration tx is the only gas cost.
0gzk key 0x...

# 3. Publish: pins the bundle to IPFS (CIDv0), then registers on Base Sepolia
#    with metadataURI = ipfs://<cid>.
0gzk publish ./circuit_bundle --network base-sepolia --register

# 4. Resolve and prove against the Base Sepolia registry.
OGZK_NETWORK=base-sepolia 0gzk registry get my_circuit
OGZK_NETWORK=base-sepolia 0gzk prove --name my_circuit@0.1.0 ./input.json
```

Fetching routes through the IPFS gateway automatically because the record's `metadataURI` is `ipfs://...`. Drop the `--network` / `OGZK_NETWORK` bits and the same flow publishes to **Base mainnet**, which is the default.

Freshly pinned CIDs can take a minute to propagate to public gateways — see **[Troubleshooting](/troubleshooting#ipfs-gateway-404--timeout-right-after-publishing)**.
